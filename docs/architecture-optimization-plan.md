# VISION 综合架构与性能优化设计方案

版本：v2；日期：2026-10-31；状态：设计，未实施运行时代码改造。

本方案合并 DeepSeek Harness 架构评估与“一切皆插件”讨论，作为后续实施依据。上游机制、源码出处和历史验证记录保留在 [架构评估](deepseek-harness-evaluation.md) 与 [验证证据](deepseek-harness-evidence.json)。

## 1. 总体决策与目标

采用 **稳定工程核心 + 可组合能力模块 + 统一执行管线 + 受控异步调度**。

暂缓引入 Cordis。首版能力模块为随应用发布的内置 Python 模块，启动时显式组合；不新增插件市场、任意动态导入、配置表达式语言或热重载。能力之间通过明确服务契约调用，资源随所属作用域创建和释放。

目标分别验收，不能合并为一个未经证明的“性能提升”：

| 目标 | 主要措施 | 评价方式 |
|---|---|---|
| 降低单任务完成时间与费用 | 减少无效模型往返、重复上下文和确定性工具步骤 | 任务成功率、端到端时间、真实 token 与费用 |
| 改善多任务响应 | 独立模型 I/O、有界调度、公平准入 | 其他项目就绪任务的排队与推进延迟 |
| 提高可维护与可替换性 | 模块契约、工具注册、启动组合 | 新工具或替换适配器需要修改的稳定核心范围 |
| 保持工程可信性 | 版本围栏、事务、完整证据、来源失效检查 | 正确性与恢复测试零退化 |
| 改善界面反馈 | 有界进度、增量读取、按需流式 | 状态可见延迟、传输量；单独统计首 token 时间 |

## 2. 依据及验证边界

本方案依据上游固定提交 `ce7073d51254c26cd63b22a60835b8f948deb447` 和 VISION 当前工作区；前序评估记录本地 HEAD 为 `3477957e47a502e159678c588f2e9bba6d764104`，并明确包含既有未提交修改。

已验证与已确认事实：

- 前序普通本机回归共 105 项，102 通过、3 跳过。该结果是设计前基线，不能作为改造后的验收结果；本次文档整合没有重跑这些测试。
- 隔离探针调用实际 `Tasks.loop`，复现单项等待阻塞其他任务推进；模型等待本身使用可控事件，不是远程网络实测。
- 完整注册 schema 共 25 项、29,944 字符；本地生成 p50 约 18 ms。基础 SYSTEM 为 12,738 字符。它们不是过滤后的代表性请求，也不是 provider token 数。
- 当前任务线程同步等待 `provider.complete()`；请求取消没有贯穿传输；关闭 join 时间与请求总超时不匹配，均已对照代码。
- 本项目已经有阶段裁剪、只读同类合并、API 缓存、几何摘要、脚本引用、检索脏队列和缓存、模块化建模、请求快照及持久原生任务，应持续复用。

尚未验证：拟议结构的真实提速幅度、连接复用收益、阶段提示对模型成功率的影响、扩大只读批量的实际收益及大历史项目 p95。没有远程模型 A/B，也没有执行上游完整测试；所有性能门槛均为实施后的目标。

## 3. 目标架构与依赖方向

```text
React 工作区 / HTTP API
            │
应用组合入口：配置校验 → 依赖校验 → 装配 → 启动 → 关闭
            │
任务协调器 ───────────→ 模型 I/O 服务 → 已装配模型适配器
    │                         │
    │                    完成 / 失败 / 取消通知
    │
    ├─ 上下文编译器 ← 内置上下文贡献模块
    ├─ 本步工具准入 ← 工具注册表 / 阶段策略
    └─ 执行管线 → 能力模块 → 工程命令入口
                                  │
稳定工程核心：SQLite / revision / CAS / epoch / 来源 / 作业 / 制品 / 证据
                                  │
原生执行适配：现有 CAD、FEA、查询进程与资源限制

观测与通知：接收执行事实，产生指标和 UI 更新
```

依赖向下：模块依赖服务契约；协调器不导入具体模型厂商或求解器实现。模块间直接调用明确的服务方法；只有通知、观测和少量显式扩展点使用事件/钩子。

首版可替换能力集中在模型适配、工具与上下文。CAD/CAE 先封装现有适配边界，第二种实现出现前不建设完整通用求解器框架。React 组件保留当前组织，不同时建设前端插件系统。

## 4. 稳定工程核心的职责与不变量

核心继续拥有下列决定权：

1. 项目、revision、head 和工程对象身份；每次写入的 CAS、幂等与事务。
2. task epoch、任务纠正/取消、所有权和持久状态转换。
3. 来源的可用性、失效、遗忘及派生内容处理。
4. 原生作业准入、资源预算、制品验证和采纳。
5. 工程证据与输入版本的关联，数值检查和完成等级判定。

能力模块通过核心命令服务请求变更，不能绕过正式路径直接更新 head、操作其他模块的数据库表或采纳制品。能力模块均是受信任的应用代码；这些边界首先由 API、依赖规则与测试约束，并不构成不可信插件沙箱。

不可削弱的规则：

- 模型输出、摘要或模块成功返回不等于工程验收通过。
- manual / unknown 不能因上下文压缩、批量查询或减少轮数而变为 verified。
- 过期 head、epoch、preview、来源和拓扑引用不能授权当前写入。
- 失败、取消、结果未知不得触发隐式采纳或自动重放写入。
- 任何网络请求、模型等待、原生计算都不能跨越长时间数据库事务。
- 请求和证据可追溯，同时遵守现有遗忘/脱敏策略；不可借“不可变日志”无限保留应删除的来源副本。

## 5. 能力模块：契约、作用域与装配

### 5.1 首版模块契约

| 契约内容 | 约束 |
|---|---|
| `id` / 契约版本 / 实现版本 | 稳定身份；版本写入相关请求或结果，不只写包版本 |
| `requires` / `provides` | 显式服务依赖与提供项；必需依赖缺失或循环依赖时启动失败 |
| 注册动作 | 注册工具、上下文贡献项或适配器；每项均有撤销动作 |
| 启动动作 | 在所属作用域创建连接、异步任务等资源；完成后才开放准入 |
| 关闭动作 | 停止准入、取消、排空、释放；支持重复调用且不重复执行效果 |
| 配置 | 启动时校验；只接受已知内置模块与字段；不执行配置中的代码 |

首版注册表为不可变定义及显式装配函数，不实现通用 IoC 容器。仅在应用组合入口解析依赖和绑定服务，避免业务模块任意查找全局 service locator。

同一作用域同一服务仅允许一个明确提供者；工具名称重复直接失败。可选检索能力缺失可以按已定义策略退回词法检索，但必须在回执和指标中记录降级；核心存储或数值后端缺失不能静默替换为模拟实现。

### 5.2 作用域与所有权

| 作用域 | 拥有内容 | 释放时机 |
|---|---|---|
| 应用 | 内置定义、配置、观测订阅 | 进程关闭 |
| 工作区 | 核心服务、模型 I/O 循环、检索缓存、原生控制器 | 工作区关闭 |
| 任务 epoch | 在途请求、等待结果、取消句柄 | 纠正、取消、删除或结束 |
| step / attempt | 已准入工具集、上下文快照、工具调用身份 | 本步结算或中断 |

先不增加项目专属插件实例。应用支持多个工作区时，也不能把全局可变客户端或缓存误共享为工作区事实。

### 5.3 启动、失败与退出

启动按“配置/依赖验证 → 核心与所有权 → 模块注册及资源初始化 → 恢复持久状态 → 开放任务准入”。任何阶段失败，都逆序释放已获得资源，避免留下线程、监听器、连接或控制器锁。

正常退出按“停止准入 → 发出取消 → 结算已知结果 → 排空模型/查询/原生活动 → 关闭客户端和订阅 → 释放工作区所有权”。超出受控关闭期限必须报告未排空状态并保留所需所有权，不能把仍运行的任务伪装成已退出。

首版通过重启改变模块组合。禁用模块只影响新启动配置；已有未知请求仍按既有恢复规则暂停，不因重新启用模块自动重发。

## 6. 统一任务与模型请求生命周期

### 6.1 消除队首阻塞

保留一个任务协调器负责状态推进和持久提交；新增一个工作区级异步模型 I/O 服务。协调器持久化请求并提交 I/O 后立即返回，后续消费完成结果，而不是在 `step()` 内同步等待。

首版最多 2 个模型请求并发，以实验确定最终值；每个 task 最多 1 个在途请求。同项目保持现有写入与决策顺序，不因放开 I/O 就允许相互依赖的任务同时修改。原生作业单通道和查询单槽保持当前约束。

项目调度名额只约束受调度的活动步骤，不是跨等待期的数据库锁。等待用户时释放调度名额；等待持久作业时协调器仍可结算事件。用户手工编辑继续遵守现有 CAS，后续模型/作业结果根据原始版本决定失效、保留历史或成为候选，不通过全程锁住项目来防止冲突。

公平准入采用有界待执行队列，按项目轮转，不用长事务持有项目锁等待网络。需为同项目后续纠正/取消保留可推进控制通道。队列满时显式返回忙或保持有界等待，不无限创建 future。

### 6.2 请求身份与持久化

每次 attempt 固定 task、epoch、turn/attempt ID、base revision、来源依赖、模型选择、工具准入摘要、上下文摘要和策略版本。完整发送负载继续沿用已有压缩快照；digest 不能代替快照本身。

复用现有 `agent_turns` 与快照体系承载请求；通过兼容性迁移补必要元数据。批量工具另加子调用记录，不提前建设一套平行的 Session 日志。

概念状态为“已保存 → 等待准入 → 请求中 → 已返回/失败/取消/未知 → 工具准入与结算”。这是设计中的内部请求状态，不要求马上替换产品现有 task 状态枚举。

协调器区分“本进程 I/O 服务仍拥有该请求”和“重启后只剩 requesting_model 持久记录”。前者等待完成；后者按结果未知暂停。不能沿用当前同步代码中遇到任何 pending 请求就判断为中断的处理。

### 6.3 结果与取消竞态

完成消息携带固定请求身份，协调器在事务内核对任务状态、epoch、head、来源和重复完成情况。通过后才能开放工具执行；失效结果不能写入新 epoch。可保留允许保留的请求身份、已知 usage 和失败分类，但不得恢复被遗忘内容。

取消/纠正先由事务推进状态或 epoch 并取消拥有的作业，再通知请求所有者中止 I/O。通知存在延迟时，事务围栏仍负责拒绝迟到操作。若收到响应后、提交工具前发生纠正，结果同样失效。

AsyncClient 在所属事件循环中创建、使用和关闭。连接复用顺带实现，但计入网络耗时后再判断收益。模型适配器只负责请求序列化、传输、完整响应解析及错误归一化；供应商无关的工具合并与预算策略归执行核心。

网络结果未知不自动重发。明确的本地参数拒绝可以在修正后生成新 attempt；供应商拒绝、限流和服务错误先分类，自动重试必须以后单独定义可受理条件、次数和费用预算，首版不放开。

## 7. 工具契约与统一执行管线

### 7.1 单一工具定义

在 `TOOL_MODELS` 基础上收敛：名称、描述、模型输入 schema、服务器命令 schema、适用阶段、前置证据、handler、资源通道、并发分类、预算、规范结果、模型投影及版本。

不是每个工具都必须实现空钩子。先用只读工具与一个现有构建工具验证定义足以表达现状，再迁移其余工具；新工具应通过增加定义/实现和装配完成，无需增加 Agent 主循环分支。

### 7.2 本步准入

依据当前 revision、epoch、阶段、已有证据、模块组合和剩余预算生成一次 `ToolAdmission`。同一对象用于模型 schema、返回参数检查和执行解析。

服务器字段不能由模型指定。模型输入通过本步 schema 后，服务器注入幂等键和版本，展开保存的 preview，再通过完整命令 schema。保留 `build_geometry({})` 引用当前有效预检的语义。

schema 缓存按工具定义/投影版本区分。动态裁剪使用独立副本或不可变结构；不能把同一可变 schema 在分析/建模之间反复删字段。

### 7.3 执行阶段

```text
已准入调用
 → 校验身份、schema、预算、版本和来源
 → 应用受控策略
 → 核心最终检查（拒绝不可被后续扩展翻转）
 → 资源准入与执行
 → 核心事务/制品结算
 → 完整规范回执
 → 模型投影 / UI 展示 / 指标通知
```

实际工程命令在提交事务中再次检查 head/epoch 等约束；前置检查不能替代该原子检查。结果投影失败不得导致已经提交的写操作被当作未执行而重跑，应保留正式回执并报告展示失败。

日志和性能观察者异常被隔离；改变工具准入或参数的策略必须失败可见，不能吞异常后继续执行。首版仅为已有需求设置有限钩子，不创建可随意重排的通用 middleware 生态。

## 8. 批量与并发执行设计

业务只读、线程安全、版本稳定是三项独立条件。默认独占，只有验证过的能力和参数组合可并行。

| 工具类型 | 首版策略 |
|---|---|
| API 文档、限定脚本/回执读取 | 可纳入只读批次；文件和身份必须固定 |
| 拓扑列表、artifact 指标 | 固定 artifact 后可批量；尽量读取已有制品 |
| 原生 inspect | 复用当前合并和单槽；不直接增加原生并发 |
| 检索 | 维持现有锁和索引更新语义；不得因业务只读就默认并行 |
| preview、配置工况、remember、需求/模块登记 | 独占；preview 回执也会影响后续步骤 |
| build、solve、ask_user、finish | 独占并保留现有任务语义 |

先扩大只读批量，再考虑工具 body 的并行。每批最多 4 项，所有参数在执行前完成校验；混合读写批次整体拒绝，零执行。合法纯读批次中的运行失败各自结算，不丢弃已经成功的结果。

模型结果顺序与输入调用顺序一致；UI 可展示某项已完成，但下一模型请求读取正式结算后的完整批次。每个 call 有独立 ID、状态、参数摘要和回执引用，另有 batch ID 关联；保持现有单调用记录可读。

取消时停止启动新项，已启动项取消或排空，未启动项补 cancelled-before-start 结果。进程中断后不自动恢复写批次；首版只读批次也先暂停，由恢复策略判断是否可重读，而不是复用未知身份执行。

减少往返不以猜测依赖为代价：如果第二项参数必须从第一项输出确定，则顺序执行，不能一次提交猜出的 face ID 或参数。

## 9. 上下文、提示词与工程记忆

上下文编译器接收内置贡献模块，输出一个统一、版本化、受预算约束的快照。贡献模块返回结构化数据、来源/版本、重要级别、体积及展开引用；不能各自直接拼接 SYSTEM。

| 内容 | 保留策略 |
|---|---|
| 当前请求、明确纠正、授权、原始目标 | 必须保留；过长时明确指出未完整容纳并提供原文引用 |
| 工程真相、当前物理输入与来源、版本身份 | 高优先；不能被历史摘要覆盖 |
| 最近失败、当前关键回执和未完成项 | 高优先，支持恢复与避免重复工作 |
| CAD API 文档、历史脚本与拓扑 | 优先签名/摘要/引用，具体需求时展开 |
| 旧阶段摘要、普通历史、冗余数据 | 预算内择取并记录省略 |

若必须内容无法装入硬预算，明确阻止该次请求或要求缩小范围，不能悄悄截断关键约束后继续执行。

SYSTEM 拆为公共规则及建模、分析、模块装配规则。公共工程约束始终存在；阶段规则来自同一策略版本。稳定排序和固定前缀有利于评估缓存，但缓存收益以 provider 返回和实际延迟为准。

保留当前独立请求与完整快照模式，不同时迁移原生 assistant/tool 历史协议。对超长历史先做确定性投影和按需展开，再根据实验决定是否引入额外模型摘要。

规范回执、模型摘要和 UI 展示彼此分离。普通规范回执保留现有上限；大结果使用受限文件和 digest 引用，保留来源关系、展开权限及遗忘/导出策略。日志、缓存和 UI 不得成为被遗忘来源的旁路副本。

## 10. 减少确定性往返与增量计算

- 构建回执已有 modeling_check / geometry_summary 时，直接供后续解释，保持只在证据缺失或输入变化时检查。
- solve 成功后的确定性 assessment 可作为受控后置步骤生成：独立保存输入版本和正式回执，再让模型解释；缺证据仍为 unknown。实施前确认它没有依赖用户新决策。
- 重复查询按 runtime、artifact、参数和来源有效性复用；不根据自然语言近似匹配复用数值结果。
- 使用现有参数 replay、局部 script edits、代码模块与 assembly 缓存，避免重发整段代码、重复构建未变零件。
- preview 与 build 保留可中断边界。预检信息变化、head 变化或用户纠正必须阻止旧输入执行，不直接自动合并两步。
- 本轮不改 FEA 数学和网格策略，也不以小残差替代网格精度；这些属于独立数值验证。

## 11. 检索投影与缓存一致性

当前热路径在结果缓存命中前仍读取/序列化来源集合，应先用大历史数据测量，而不是再增加一层相似缓存。

测得收益后，为项目 sources 增加事务内 generation。首选通过 SQLite 触发器覆盖 sources 的 insert/update/delete，避免遗漏现有直接 SQL 写入；迁移、导入、项目删除和回滚都要验证。generation 是失效标记，不能替代来源是否适用的业务检查。

上下文与检索缓存 key 纳入 project/revision/epoch、source generation、runtime、策略及模型版本、查询和预算。读取只在身份匹配时复用；缓存落后允许重算，不能领先核心已提交事务。

首版使用有界工作区内存缓存；没有冷启动收益证据就不持久化缓存。若后续持久 checkpoint，必须包含高水位和 schema 版本，失配丢弃重建。来源遗忘立即清理派生内容并使相关任务失效；最终请求发送和结果提交仍检查来源。

## 12. 原生执行、UI 与观测

原生进程继续使用现有 ProcessTree、内存限制、超时和原子制品发布。能力封装不得把受控进程改成主服务内直接执行用户脚本。常驻进程池仅在启动/加载成本占比显著且崩溃、句柄消耗、内存清理可控后再评估。

UI 优先改为终态停止高频轮询、游标增量与自适应间隔。需要流式反馈时再增加 SSE；持久状态通过游标恢复，瞬态 token 单独传输。完整工具参数通过校验前不得执行，断线不取消已经提交的持久原生任务。

观测沿用 task/epoch/turn/request/call/job/revision 标识关联。分项计时覆盖上下文、检索、schema、模型排队与等待、工具资源等待、原生排队/执行、取消排空。使用 monotonic 计时；统计记录 ID、计数和 digest，避免复制项目正文。

provider 实际 token、缓存与 reasoning 用量按可用字段校验，缺失为 null；字符/字节估算单列。费用仅在价格来源、日期和计费字段完整时计算，不能把估算冒充账单。

## 13. 代码落点与迁移原则

以下为职责落点，不要求一次拆出同名文件或建立空框架：

| 现有位置 | 拟议职责变化 |
|---|---|
| `api.py:create_app` | 作为显式组合入口，集中资源启动、失败回滚与关闭 |
| `tasks.py` | 保留协调与状态推进，消费异步完成结果，减少等待型操作 |
| `model_tasks.py` | 分解请求准备、提交、结算；保留快照、用量、修复与围栏 |
| `provider.py` | 提取模型适配职责；通用工具合并和阶段策略移向核心 |
| `task_tools.py` | 迁为统一定义及现有 handler；复用 `prepare` 和工程命令入口 |
| `task_memory.py` | 统一编译、预算与贡献项组装，保留关键事实保护 |
| `retrieval.py` | 保留检索实现，按实测引入 generation 失效 |
| `jobs.py` / `queries.py` / `processes.py` | 先保持执行语义，仅接入统一资源所有权与观测 |
| `storage.py` / `migrations.py` / `bundles.py` | 只做必要的兼容元数据迁移；保持事务与导入恢复规则 |

每步先把现有行为封装进新边界，做等价对照，再改变执行策略。避免在同一批同时重写 schema、模型协议、数据库和 CAD 后端。现有未提交改动必须单独识别，不能被架构迁移覆盖。

## 14. 分批实施与依赖

| 批次 | 内容 | 依赖及验收出口 |
|---|---|---|
| A：基线 | 指标、代表任务、请求/schema 金样、竞态测试夹具 | 不改变行为；具备比较和定位能力 |
| B：能力边界 | 内置模块装配、所有权、统一工具定义、单步准入；包装当前同步模型调用 | A；现有回归等价、启动失败清理通过 |
| C：异步生命周期 | 模型 I/O 服务、公平有界队列、取消、完成结算与关闭 | A+B；队首阻塞消除、重复完成和重启恢复正确 |
| D：上下文与轮次 | 阶段提示、贡献项、回执投影、确定性 assessment | B；金样完整性及端到端成功率验证 |
| E：只读批量 | 子调用记录、批次准入、部分失败/取消结算 | B+C；持久批次与调用身份验证通过 |
| F：条件优化 | generation 缓存、增量 UI、流式；必要时 worker 实验 | A 的实测收益触发；不作为前面批次的前提 |

B 只封装首批必要边界，不等所有能力都插件化才进入 C；C 的调度问题优先修复。D 与 E 可分别评估，不能因为批量功能就默认改变所有任务的规划策略。

首个实施单元建议为：A + B 中的模型服务边界和工具准入试点 + C。CAD/CAE 后端暂时作为原样适配器接入，避免为框架完整性扩大改动。

## 15. 测试、实验与验收

### 15.1 必过正确性矩阵

| 领域 | 场景 |
|---|---|
| 装配 | 缺依赖、重复服务/工具、循环依赖、启动中途失败、重复关闭 |
| 模块替换 | 模型 mock 替换真实适配器无需改主循环；禁用工具后新请求不可见也不可执行 |
| 调度 | 慢/快跨项目、同项目顺序、队列满、单 task 单在途、结果重复投递 |
| 取消 | 请求前、发送中、返回后未提交、工具执行中、关闭中；epoch/来源失效竞态 |
| 工具 | 投影 schema 一致、额外字段拒绝、无效 preview、call ID 唯一、server-owned 字段保护 |
| 批量 | 混合写入零执行、纯读部分失败、结果保序、取消补结果、中断后暂停 |
| 工程 | head CAS、幂等、拓扑失效、原子制品发布、迟到结果不采纳、数值证据绑定 |
| 上下文 | 原始目标/授权/纠正保留、失败恢复、关键内容超预算时不静默丢弃 |
| 缓存 | 删除/supersede/forget、导入、重启、高水位、版本失配、项目隔离 |
| 恢复 | 已提交副作用不重跑、未知模型请求不重发、活动导入任务暂停、旧 bundle 可读 |

旧回归覆盖基础行为，新测试只补新增边界与风险。触及真实 CAD/FEA、制品和 UI 时运行相应集成验收；不能用 mocked provider 测试声称真实模型任务成功率提高。

### 15.2 性能实验

沿用前序 12 类代表任务：首次建模、参数修改、模块装配、布尔失败恢复、预检变化、定向复核、已有工况、缺物理输入、长历史、来源遗忘、跨项目慢快、取消关闭。

离线回放用于验证结构化输入与调用行为；真实原生固定输入用于验证几何/数值一致性；真实模型 A/B 用于验证轮次、完成时间、成功率和费用。A/B 固定初始工程、模型与策略版本，交错运行，区分冷暖缓存；每类至少 5 对作为探索起点，样本不足不宣称统计显著或成功率等价。

来源规模使用 100 / 1,000 / 10,000 条，分别测缓存命中、失效和遗忘。热路径至少 100 次记录，冷启动独立报告。远程样本的 p95 不凭少量样本给出稳定结论。

### 15.3 发布门槛（目标，不是已实现收益）

- 受影响正确性测试全部通过；原生几何与数值验证满足既有容差。
- 可控慢模型等待期间，其他项目就绪本地任务推进等待 p95 < 500 ms；同项目顺序不变。
- 可控网络夹具下取消至本地请求排空 p95 < 1 s；不包括原生进程的另行清理时限，也不承诺供应商停止计费。
- 适用上下文样本目标减少至少 20% 实际输入 token 或请求字节；两者分列，关键事实完整性全部通过。
- 适用只读批量至少省一次模型往返，结果身份和失败可诊断，无新增工程写入。
- 替换模型 mock 或增加只读工具不修改 Agent 主循环；模块启动失败后无遗留资源。
- 端到端收益不足或成功率存在未解释下降时，不默认启用优化策略。小样本结果只作为继续实验依据。

## 16. 发布、回滚与暂缓项

每批独立提交与验收。模块/策略版本写入任务元数据，在途步骤按既定快照结算；不能运行中将其解释为另一版 schema。可保留短期旧路径做受控对照，完成迁移后删除，不长期维护两套真相。

运行时回滚先停止准入并排空，再切回旧策略。新增数据库结构优先使用兼容的增量迁移，旧任务继续可读；回滚程序不等于回退已提交工程 revision。派生缓存可丢弃；未知请求不能因回滚自动重发。迁移前沿用现有备份机制，并验证 bundle 导入导出。

暂缓：Cordis、通用依赖注入容器、插件市场/热重载、任意 PTC、同工程多 Agent 并发写入、全面 Session 日志替换、模型历史协议迁移、原生并行度扩大，以及未经测量的常驻 worker。

重新评估 Cordis 的触发条件是：多产品/多宿主共享插件、复杂动态依赖和热卸载成为明确需求，且 Python 边界实现的维护成本已有记录。届时再比较跨运行时成本与实际收益，不以“已有框架”作为迁移理由。
