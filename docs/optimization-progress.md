实施依据：[综合设计方案](architecture-optimization-plan.md)。不引入 Cordis。

## 基线

2026-10-31：既有工作区源码、测试、启动脚本和设计文档保存为 `17d29c3`，推送到 `origin/codex/cleanup-retired-code`。

## 第一批：模型生命周期与工具准入基础

- 请求拆为准备/保存快照、传输、结算。生产后台使用工作区独立异步 I/O 服务，最多两个在途请求、共享受控 HTTP client；手动离线单步入口保留同步传输，协议校验与结算代码共用。
- task 单在途、同项目决策串行，跨项目按轮转推进；等待原生作业仍可结算。模型等待不再占用协调器线程。
- 纠正、取消、来源遗忘通知 I/O；协调器回收其他路径造成的过期请求，包括项目停止/删除和 head 变化。迟到响应仍经过原有 epoch/head 围栏。
- 关闭停止准入、取消传输、等待清理，暂停未结算请求并保留未知结果说明；启动失败进入清理路径。
- 记录上下文/负载准备耗时、负载字节、工具数量和准入摘要，复用模型回执的实际用量与耗时。
- 工具 schema 缓存不可变序列化模板，阶段裁剪获得独立嵌套副本；每步固定准入快照，并在服务器展开前检查工具名称、顶层允许字段与必需字段，类型/嵌套/命令语义继续由现有 Pydantic prepare 校验。

验证：定向运行 `test_model_io_v2`、`test_tool_admission_v2`、`test_model_tasks_v2`、`test_tasks_v2`、`test_context_efficiency_v2`、`test_agent_orchestration_v2`，共 52 项，50 通过、2 个原生可选检查跳过，耗时 55.523 秒。测试使用临时工作区及可控传输，没有远程模型调用。此前首次异步测试连同原有模型协议测试 18 项通过。

边界：验证了功能隔离、取消、关闭、回执、快照、来源和版本保护；没有声称已测得 p95 调度目标、真实模型提速或费用收益。工具统一注册/handler 迁移、阶段上下文、只读批次持久化及大历史缓存仍待后续批次。

## 第二批：内置工具能力注册表

- 25 个工具的模型、描述、handler、阶段、只读分类与资源通道收敛为不可变内置注册表。阶段过滤读取注册表；执行按注册 handler 分发，不再使用共享 execute 的长条件链。
- 原有 prepare、事务命令、来源过滤与数值 handler 内容保持；未知工具明确拒绝，模型/handler 集合不一致在导入时失败。
- 保留 TOOL_MODELS 只读兼容视图，新增工具不需要修改 Agent 主循环。不引入动态插件加载。

验证：提取前后完整工具 schema 序列化逐字一致；工具命令、代码模块、分析上下文、求解校核与准入定向回归 37 项，35 通过、2 个可选原生检查跳过，耗时 56.333 秒。没有重跑模型 I/O、完整 UI 或完整数值套件。

## 第三批：阶段提示贡献与上下文成本记录

- 公共约束、建模规则、分析规则按阶段组装；模块装配说明仅在模块模式出现。完整旧提示保留为离线基线文本，不再每轮全部发送。
- 首次分析请求可能仍处于建模阶段，因此公共提示始终保留分析入口、物理输入来源和建模不自动授权求解的约束。
- 请求元数据记录提示策略版本、实际 SYSTEM/工具 schema 字符数及各上下文段大小；字符指标不冒充 token。

验证：公共约束、阶段规则、分析上下文、编排与上下文回归共 25 项通过；补充分析入口约束后仅重跑 3 项提示定向检查，全部通过。固定同一简单上下文与工具集合的离线对照：建模请求 34,525 → 30,877 字符（减少 10.6%）；分析请求 26,698 → 21,855 字符（减少 18.1%）。这些是结构性输入减少，不是实际 token、延迟或成功率的 A/B 结果。

## 第四批：有界只读批次

- 新增 read_batch，一次最多 4 个相互独立的来源、脚本、回执或拓扑读取；沿用已有同类 native_api 合并，不扩大原生查询通道。
- 子调用须在本步工具集合中可用；全部参数在任何读取前校验，写入/嵌套批次整体拒绝。文本范围最多 2000 字符、拓扑最多 8 项，单结果超过 3000 字符明确失败，批次结果限制在现有回执预算内。
- 子调用在现有 durable turn 的 receipt 中逐项持久化 ID、参数、状态与完整结果；不新增表或第二份状态真相。结果可经 read_tool_result 展开，并沿用工程包导出/导入和来源遗忘。
- 部分失败保留其他结果；纠正/取消补齐未开始项，迟到结果不采用；中断中的子调用暂停而不自动重放。批量同样受准备阶段和重复查询 watchdog 限制。

验证：新增 5 项批量检查通过；同时相关模型协议、任务与准入检查 27 通过、2 个可选原生检查跳过。首轮唯一报错是新增测试夹具缺少 revision，修复后只重跑 5 项新增检查（7.510 秒），未重复其他已通过套件。没有真实模型 A/B，尚不宣称模型会自动选择最优批次。

## 第五批：有测量依据的检索热路径优化

- 在一次性词法检索工作区构造 10,000 条约 200 字符来源。原路径即使命中结果缓存也读取/验证全部来源与 chunks，并序列化全文生成 key；12 次重复查询 p50 134.421 ms。
- 利用已有 retrieval_state 增加来源 generation，SQLite 触发器覆盖插入、修改、删除及跨项目更新，与来源事务共同提交/回滚。没有改变数据库表布局或 bundle 字段，generation 是可重建派生状态。
- 缓存 key 使用 generation、revision、查询、预算、语义配置及模型文件版本；热命中在加载全文和候选集前返回。冷路径的推理后来源复核、模型请求前与工具提交前的围栏保持。

同一夹具优化后 12 次查询 p50 3.939 ms、最大 6.181 ms；原路径最大 172.610 ms。结果见 [基准记录](retrieval-generation-benchmark.json)，当前实现可用 `.python313/python.exe scripts/benchmark_retrieval.py` 复现夹具。只比较本地词法检索热路径，不代表上下文整体或模型任务收益，也没有用 12 个样本宣称稳定 p95。

验证：来源 generation、热命中 SQL 路径、事务回滚、跨连接修改、删除、检索与记忆/导入相关 21 项检查通过，耗时 6.927 秒；一次性基准工作区已清理。

## 第六批：故障收敛与执行计时

- 模型 I/O 服务关闭/失效时，新步骤明确暂停，不因“没有可用名额”无限等待。
- 调度快照/请求回收失败会记录并重试，不直接使协调线程退出。
- 传输失败保存耗时和失败分类；成功工具保存执行耗时与资源通道，API 仍隐藏参数，只增加 execution 统计。启动失败、关闭服务、失败不重发和既有取消路径共 9 项定向检查通过，耗时 11.870 秒。
- 更新代码地图、后端说明和设计文档状态；没有引入新的依赖或 Cordis，没有改变 CAD/FEA 数学、原生并行度或工程采纳规则。

## 后续条件项

真实模型任务的成功率、完整延迟及实际 token 需要独立 A/B，本轮未调用远程模型。自动 assessment、进一步上下文贡献接口、增量 UI、持久投影和常驻 worker 仍按设计中的收益/正确性条件推进，尚未默认启用。当前本地收益不可外推为整条 Agent 链路的固定提速倍数。

## 第七批：实际批量限额失败的恢复与用量口径

真实暂停记录显示：read_batch 请求 3600 字符，超出 2000 字符上限。旧实现把这一限制写在 schema 之外，并抛出普通 ValueError，未进入模型参数拒绝/有限纠正分支，导致首次参数错误就直接等待用户。

- 将批量子参数改为有界 Pydantic 契约：文本 limit 上限进入模型 schema，拓扑额外限制也作为模型校验错误返回。复用已有 rejected/有限纠正逻辑，不放宽限额、不裁剪后执行、不无限重试。
- API 增加 current_epoch_reported_tokens；对话界面分别标明本轮上报用量与对话累计上报用量。累计值继续跨消息保留，避免把既有费用/用量历史清零掩盖问题。

验证：复现 3600 字符错误后成功纠正、重复错误有限暂停、跨 epoch 用量、既有批量持久化/取消/遗忘共 8 项通过（21.632 秒）；前端 typecheck 通过。仅使用隔离临时工作区和模拟模型，未重发真实用户任务。
