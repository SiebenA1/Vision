# 输出截断与局部脚本通道第一步

轮辋修改任务0dae292b…第4轮的建模要求输出使用10,843 completion token；第5轮多个工具调用被拒绝；第6轮输出达到16,384 token并以length结束。由于原始回复没有保存，不能断言截断全部来自源码；completion还可能包含推理。旧逻辑将不同协议错误共用一次重试，因此第6轮首次截断后立即暂停。

修复内容：

- 保持16,384输出上限；不执行截断调用，不直接提高预算掩盖问题。
- 区分multiple_calls、truncated_output、missing_tool_call及参数/完成声明错误。不同连续错误可获得对应纠正机会；同类连续第二次或连续第三次拒绝仍暂停，避免循环。
- 截断纠正明确采用低推理、局部修改或单个组件构建，不重新输出长装配程序。
- preview_build增加script_edits和base_script_sha256；后端读取不可变source.py，确认基础哈希匹配，按顺序执行每个唯一精确替换，验证完整脚本后保存预检。随后仍由build_geometry({})执行精确预检输入。
- 原始代码不被覆盖。参数重放、当前工程版本/epoch围栏、制品文件校验和及原生错误分类保持生效。
- 需求登记导致工程版本变化但几何制品不变时，可继续使用同一制品的已读取脚本，避免无效重复读取。
- 回执仅增加输出字符数、工具参数字符数、推理字符数及供应商提供的reasoning token计数；不保存原始推理内容。拒绝回执补充耗时和安全的已知工具名，用于后续定位输出膨胀来源。

真实CAD测试以7×2×3盒体为基础，局部替换宽度为4，验证体积从42变84；基础源码保持不变。匹配不到、多处匹配或基础哈希不一致均拒绝。混合“多调用→截断→正确回复”测试验证前两次不执行工具，第三次可完成。

这只是代码制品通道的第一步。独立模块目录、代码检索与依赖增量执行仍属 [后续架构设计](modeling-code-channel-design.md)。

最终验证：76项关键流程测试通过，额外37项中34项通过、3项可选原生集成跳过。真实CAD局部修改、基础版本与歧义拒绝、不同错误的有界恢复均通过；未重发用户工程的远程建模请求。
