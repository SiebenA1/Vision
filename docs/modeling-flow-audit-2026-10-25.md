# 自然语言建模流程功能审核

审核日期：2026-10-25。审核对象为当前工作区实际文件，包括尚未提交的 v2 实现；不等同于 Git HEAD。

修复状态更新：本文保留修复前审核证据。执行闭环、关键上下文和记忆失效的第一阶段修改与验证结果见 [建模修复进度](modeling-fix-progress.md)；复现脚本已改为修复后的回归入口。

## 结论

存在设计缺陷与功能 bug，能够共同解释多轮交互中的反复查接口、重复确认、失败后无法自主修正、建模结果反馈失真。主要断点在“规划—执行—观察—更新目标”的闭环，不能仅归因于模型能力或向量数据库质量。

离线复现了 **9 类问题，共 10 个断言检查**。其中 7 类按 P1 处理，2 类按 P2 处理；另列 3 项有明确代码依据、尚需规模或并发测试量化的设计风险。P1 表示会直接破坏目标、对象、记忆或执行闭环，应优先修复；没有认定为数据永久损坏或系统不可用的 P0。

本次只新增审计报告、离线复现脚本及证据文件，没有修改业务实现、现有工程数据库或已有建模脚本，没有调用远程模型。测试用的新工程均在隔离临时目录。

## 实际链路

```text
CoreWorkspace / ConversationPanel
  → POST conversation：校验 head/task/epoch，保存用户来源，取消旧 epoch 的未完成工作
  → Tasks.loop / step：推进持久任务
  → task_memory.context：工程文档 + 用户消息 + 工具组 + 记忆 + 历史检索 + CAD 接口
  → retrieval.retrieve：增量分块/FTS → 本地 embedding/Qdrant → 融合 → cross-encoder → 来源去重
  → provider.payload：裁定可用工具；把编译 JSON 作为一条 user 消息发送
  → model_tasks.next_step：保存请求快照 → DeepSeek → 协议/参数校验
  → task_tools.prepare / execute：查询、预检、提交 CAD 作业等
  → Controller / native / usd_brep_worker：原生执行、制品验证、成功后采用几何版本
  → Tasks.step：保存工具回执；成功步骤才进入后续上下文
  → ask_user / finish：保存阶段摘要并暂停/结束
  → 前端每秒轮询对话、工程版本、作业和评估，显示最新几何
```

当前入口 `src/main.tsx` 加载 `CoreWorkspace`。本次主结论针对 `backend/vision`，没有把旧 `src/services/agent.ts` 和旧 `server/agent_memory.py` 的独立 agent 实现误认成主链；其中旧模块的 `search_tokens` 仍被新检索实现复用。

## 本地实测记录的交叉证据

以只读 SQLite 连接检查 `.vision-workspace/workspace.sqlite3`，脱离主工程保存的统计见 [modeling-live-evidence.json](modeling-live-evidence.json)。

- 全库有 59 次成功的 `native_api`，21 次成功的 `preview_build`；`build_geometry` 为 2 次步骤成功、5 次步骤失败。任务步骤与独立作业统计口径不同，不能用两者相除得到成功率。
- 最近持续对话为 epoch 10，13 次模型请求，最终 `waiting_user`；原生 CAD 作业 `c56b7239bd5e422b84f92f9d14b6b3cd` 超时，stdout 只记录到 `stage: native CAD build`。没有足够阶段信息定位到具体布尔运算或导出操作，不能据此断言是某一个 CAD API 卡死。
- epoch 9 有 11 次成功预检；epoch 7 有 13 次成功接口查询。与现有停滞检测覆盖不足的路径一致。
- epoch 6 用户当前消息是“是”。ordinal 7 的请求还包含前一轮方案 `ask_user`，ordinal 13 的请求只剩 `list_topology` 与 `read_script` 工具组。此后助手再次追问“是”确认的是哪一项。这个历史快照证明确认所依赖的方案曾从输入中消失；不能把每一次重复确认都归为这一单因。
- epoch 10 最后请求为 24,000 字符预算，实际上下文 18,947 字符；工具组层分配 6,906、使用 6,879，报告省略 51 项，阶段摘要层空置。说明“总容量还有空余”与“关键工具组已被丢弃”可以同时发生。
- 同一请求检索模式为 `hybrid_reranked`，没有降级。另以隔离数据实际加载本地模型，确实运行了 embedding、Qdrant 和 reranker，正确把“螺栓把安装耳紧固在墙面”排到首位，见 [modeling-local-semantic-smoke.json](modeling-local-semantic-smoke.json)。这只证明管线可运行，不证明复杂工程历史的召回质量合格。此次冷启动约 6.56 秒，不能当作稳定热请求耗时。

历史记录跨多个开发版本。`params` 未定义、发布目录重命名权限错误、预检 digest 不一致等旧错误已有对应修改或保护，本报告不将它们直接列为当前版本仍存在的根因。

### F01：最新观察没有最低保留保证

位置：`backend/vision/model_tasks.py:56`；`task_memory.py:54`、`:65`、`:79`、`:117`。

实际远程请求调用 `context(..., budget=24000)`。建模阶段仅把剩余容量的 30% 给工具组，按“指令参数 + 完整回执”整体决定是否装入，且最多 8 组；分区之间没有空余容量借用。`Tasks.step` 则允许单条回执到 16,000 字符。长建模脚本也重复占用工具组预算。

离线 F01：当前唯一的、8,000 字符 `read_script` 回执被整个丢弃，工具层容量 7,059，实际使用 0。该工具请求完全符合当前 `limit <= 8000` 的协议。不是所有建模回执都很大；已确认的是系统无法保证最新有效观察进入下一次规划。

更严重的是，用户短确认只有原文，没有明确关联它确认的 proposal。提议被挤出后，“是/确认/继续”无法可靠还原。阶段摘要也参与普通小分区取舍，不能保证补上这个关系。`layers.omitted_entries` 只进元数据与 UI，没有进入模型编译 JSON，模型甚至不知道哪些证据被省略。

建议：最低保留最新执行状态、最新观察摘要、当前已接受方案及未解决问题；原文脚本与大回执用引用及可展开工具，保留可追溯原文；允许非关键分区空余额度借用。确认消息绑定 proposal/阶段来源，不能靠“最近几条消息”猜。

验收：8k 读取、长预检脚本、多轮拓扑分页后，下一次请求仍能确定最新动作结果与用户确认的方案；被省略原文可按标识展开，并向规划器明确报告省略。

### F02：当前引用没有进入必保留层

位置：`task_memory.py:24`、`:36`、`:43`、`:132`。

`source.reference` 只用于构造检索 query。顶层必保留字段有 statement，没有 current_reference；对象引用仅附在 `conversation_messages` 的完整条目内。该条目超出对话分区时一起丢失。query 本身不发给模型，检索命中也不能保证包含正确引用。

离线 F02：约 5,000 字符的当前消息附 `body-9/face-2`，编译结果中该对象 ID 完全不存在。整个用户原文仍在 statement，唯独指向哪个面丢失。

建议：把当前 reference 作为必保留字段，包含 revision/artifact/selection 和是否仍有效；历史引用继续按版本过滤。

验收：长到允许上限的用户消息和 64 项选择，仍完整保留当前对象引用；预算无法容纳时明确拒绝，不能静默去掉指代。

### F03：派生记忆只检查祖先 inactive，没有检查 superseded

位置：`engineering_memory.py:28`、`:35`、`:101`。

`record(... supersedes=...)` 将旧记录标为 superseded。派生记录的 `context_eligible` 只否决祖先状态 inactive；`available` 仅验证谱系存在、未删除及无环，不代表其工程含义仍有效。

离线 F03：A=厚度3mm，B 从 A 派生“按3mm板厚计算间隙”，C=厚度5mm 并替代 A。A 不适用，B 与 C 却同时适用，B 仍可进入长期记忆。

建议：明确派生类型。基于旧约束推导的结论在祖先替代后标记需重新验证；仅作为引用证据的关联可保留历史意义。最小修复先阻止依赖 superseded 约束的摘要被当作当前约束。

验收：多层派生、替代、停用、恢复、几何变化后，旧推导不会恢复成有效约束；原文与历史依然可查。

### F04：记忆失效只覆盖新召回，没有覆盖旧回执再装配

位置：`task_memory.py:79`、`:86`；`task_tools.py:222` 附近的来源搜索与读取。

装配工具组只对 `remember` 的 source_id 做当前适用性检查，没有对 `search_sources` 和 `read_source` 回执内复制的内容做同等检查。新检索能过滤 inactive/superseded，但过去复制出来的文本会绕过过滤，继续进入 recent_tool_groups。

离线 F04：停用一条记忆后，长期记忆里已没有它，旧 `search_sources` 回执仍携带完整旧摘要进入下一次上下文。

建议：统一来源解析和上下文资格检查；复制回执重新装配时验证 source 及祖先状态。历史读取需要保留时显式标为“已停用/已替代的历史材料”，不可呈现成当前可执行要求。

验收：停用、替代及几何失效，在长期记忆、新召回、搜索回执和原文读取四条路径行为一致。

### F05：原生失败中断 agent 的观察修正闭环

位置：`tasks.py:269`、`:274`、`:305`；`task_memory.py:79`。

CAD 作业失败直接抛异常，统一转为 waiting_user 并将步骤标为 failed。不会再调用模型处理可修复的脚本错误。随后即使用户发送“继续/修复”，上下文也只选 succeeded 步骤，旧错误和失败脚本不会自动提供给模型。失败没有被 `archive_receipt` 作为可检索工具证据归档。

离线 F05a/F05b 分别确认：失败错误从编译上下文消失；失败作业使任务进入 waiting_user，而非返回规划器。

建议：区分确定性脚本/API错误、基础设施错误、用户取消、结果未知。确定性失败作为结构化 observation 返回模型，携带失败输入引用、阶段、错误与当前工程未改变的事实；允许有限、可检测实际变化的修正。结果未知、取消、权限等情况沿用专门恢复策略，不能盲目重跑。

验收：第一次脚本参数错误后模型能看到真实错误并修正，不要求用户复述；取消与结果未知不被误当作可重试的普通脚本失败。

### F06：停滞检测未覆盖预检和读取循环

位置：`model_tasks.py:19`。

`planning_progress` 只统计 native_api 与协议拒绝，实际构建/工况/求解重置计数。重复 preview_build、read_script、list_topology 并不会单独触发停滞。持续对话 unlimited=true，累计预算也不兜底。

离线 F06：12 次预检后 ready_to_build 与 recovery_required 均为 false；本地历史 epoch 9 有 11 次成功预检，是现实中存在的相关路径。多次预检可能合理，需要通过输入变化与当前缺口判断，不能仅按次数认定无效。

建议：按输入摘要、输出信息增量、已解决缺口和真实几何变化判进展。对相同输入和相同回执的循环给出结构化纠正，之后终止；保持复杂但有信息增量的建模能力。

### F07：完成状态只等于 finish 工具成功

位置：`task_tools.py:242` 附近；`tasks.py:300`；`provider.py` 的 SYSTEM 建模规则。

finish 仅校验 summary 是字符串，立即把 task 标为 completed。系统提示要求构造关键特征并检查拓扑，但后端没有建模目标、完成判据、当前版本验证证据之间的约束。`validate_cad` 校验制品结构和数值合法性，不能证明“确实建出了用户指定的浮动盘/孔槽/多体装配”。

离线 F07：通过真实模型任务状态机、模拟返回 finish“建模已完成”，在 geometry=null 的情况下得到 completed。

建议：先区分普通问答、方案讨论与建模任务。普通问答仍能直接 finish；建模任务的执行状态与验收状态分开，返回已构建、部分实现、未验证或验收通过等事实。明确的尺寸、实体数、开孔、分体要求，应关联当前 artifact 的检查；需要视觉判断的特征另留人工/视觉核验，不能用“原生执行成功”代替。

验收：无 geometry 或结果不满足明确尺寸/实体数时，不会展示为“建模验收通过”；尚未实现的功能必须在工具状态与回答中显式体现。

### F08：重排查询尾部被截掉

位置：`retrieval.py:197`；上游 query 组装在 `task_memory.py:36`。

召回接收最多 2,000 字符查询，reranker 却只收到 query[:320]。上游把当前 statement 前600字符放在最前，后接近期用户消息与选择。因此长描述的结尾、前轮约束和选择 ID，可能根本不进入重排的相关性判断。语义检索可以找到对的条目，重排仍可能把它降到默认前6项之外。

离线 F08：358字符查询的尾部当前目标 `body-9/face-2` 被截去，reranker 实际只见320字符。已复现截断，不声称这个单一用例测出了完整召回质量下降率。

建议：构造明确包含最新变更、关键参数、对象引用及未完成特征的紧凑查询，按实际分词长度约束；分别评价召回、重排与最终装配，避免只看 mode=hybrid_reranked。

### F09：空接口查询达到 recovery_required 后依然能无限执行

位置：`provider.py:102`、`:109`；`model_tasks.py:142` 附近 offered-tools 检查。

没有 CAD 接口证据且判定恢复时，可用工具依然包括 native_api。提示分支先命中“没有接口证据”，也覆盖了更具体的恢复提示。后端只在模型调用“未开放工具”时因空转中止；native_api 本来就在开放集合内，故不触发该保护。

离线 F09：连续8次空查询，最后请求已明确 recovery_required=true，任务仍是 executing，并实际请求了8次模拟供应商响应。现有 `test_unlimited_empty_query_loop_pauses_without_more_network_requests` 也因预置响应耗尽而失败。

建议：恢复状态禁止重复无信息增量的查询；如允许一次改变策略的补查，应明确区分查询签名和预期缺口。无法获得能力时结构化结束或报告具体缺失，不能继续调用同一路径。修复时保留“没有接口证据不能构建”的现有约束。

## 尚需量化的设计风险

### D01：数据库只读路径也占用写事务，轮询重复读取整段历史

位置：`storage.py:189`、`:199`；`conversation.py:9`、`:24`；`tasks.py:36` 附近；前端 `ConversationPanel.tsx:37` 与 `CoreWorkspace.tsx:158`。

所有 `workspace.db()` 都 BEGIN IMMEDIATE，包括纯 SELECT，因而同工作区的读取也竞争 SQLite 写锁。对话每秒全量扫描来源和步骤，逐条重新查询任务 config，随后 tasks.get 再加载/解析全部步骤；前端只显示当轮末步也照样接收历史。另有工程版本、作业、评估的每秒并行轮询。数据越长，这些读取越可能干扰作业回执和用户写入。

这是确定的锁与查询结构风险；本次没有用线上工作区做并发压测，未量化其实际占比。建议按读写拆分事务，来源/步骤添加适当查询索引并分页或增量读取，去除 N+1 config 查询，末步展示单独返回摘要。先测 p50/p95、锁等待与读取字节量，再决定是否需要改数据库产品；目前没有证据说明必须换掉 SQLite。

### D02：多个 agent 任务在一个线程内同步等待模型

位置：`tasks.py:212`、`:220`；`model_tasks.py:102`；`provider.py:complete`。

允许8个活跃任务，但 Tasks.loop 在单线程里顺序 step，网络 complete 是同步阻塞。一个工程的模型请求最多等待60秒，其他工程的已完成作业回执推进也要等它返回。原生作业 Controller 同样是一条串行执行通道，复杂 CAD 可占240秒。

多工程延迟是代码可推导的行为；单工程本次超时不能单独归因于这个队列。建议把模型等待与状态提交分离，限制并发，保留现有 epoch/head 并发隔离；重型 CAD 能力受限时明确显示排队与原生阶段耗时，而非都呈现“正在分析”。

### D03：检索候选按 chunk 截断后才按来源去重，且查询不随工具缺口更新

位置：`retrieval.py:193`、`:214`；`task_memory.py:36`、`:121`。

融合后先取24个 chunk，再重排，最后按 source 去重。一份长来源可占据多个候选槽位，最终唯一来源不足默认6项，其他来源在进入重排前就被淘汰。自动检索 query 依赖用户文本，未把刚失败的操作或新发现的未完成特征纳入；连续工具步骤可能一直检索相同背景。长期记忆则主要按 confirmed 和时间分配，未按当前任务相关性排序。

建议限制同源候选数量、保留来源多样性，在当前工具缺口上构造查询；检索后再按当前目标、来源状态、版本与已装配内容重排。需要用真实跨轮工程标注集测 source recall、必需约束覆盖率、最终上下文覆盖率，不能用向量命中数量替代正确性指标。

## 已有机制与边界

这些实现应保留，不应在修复中一并推倒：

- head/epoch 围栏、命令幂等及晚到响应丢弃，避免旧计划修改新工程。
- 来源和原始请求持久化、请求快照摘要校验、原文按段读取，有助于审计具体模型看到了什么。
- SQLite 触发器驱动增量索引、删除派生片段与向量；检索推理后再次校验来源可用性。
- 工程过滤、几何适用性过滤与本地模型加载，确实存在且相关测试通过。
- 预检后使用保存的精确输入，专门的 preview digest 即使大工具组被省略仍保留；这个修复解决了预检执行一致性，尚未解决一般观察和方案丢失。
- 制品校验、模型协议检查、create_box 参数与部分布尔对象重复消耗检查，可阻止若干已知错误；静态脚本检查不可能代替全部运行时与几何验收。

## 修复次序与跨环节约束

1. **先恢复执行闭环（F01/F02/F05/F09）**：当前请求、对象、已接受方案、最新结果和失败观察必须可靠到达下一轮；无效循环不能继续放行。不能只增大上下文或只改提示词。
2. **统一记忆生命周期（F03/F04）**：长期记忆、派生记忆、新检索和旧回执共用适用性规则。失效的工程约束不影响历史可追溯性，但不得再驱动当前动作。
3. **约束进展与完成（F06/F07）**：预检不等于构建，构建成功不等于满足要求，finish 不等于验收通过。按任务实际目标确定必须的证据。
4. **再提升检索与性能（F08/D01/D02/D03）**：来源多样性、任务相关查询、读写事务分离、增量历史和受控并发。当前没有依据需要引入新的向量数据库或额外 agent 框架。

建议把以下不变量作为修复边界：

- 当前用户原文、当前引用、已确认且未替代的关键目标不因普通历史裁剪消失。
- 每次规划能区分成功、失败、取消、结果未知，以及当前是否真的产生新 artifact。
- 已替代约束的推导不得继续作为有效约束；所有复制路径遵守同一规则。
- 每个已接受方案可追溯到原始提议与确认，短确认无需重新猜测。
- 模型不能通过不断查询或预检绕开无进展检测。
- 结果状态区分任务结束、建模完成及完成验证，不通过自然语言 summary 推断事实。
