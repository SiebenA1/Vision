# VISION 工程 Agent 记忆系统设计报告

版本：评审稿 v1.1 · 日期：2026-10-20

范围：ATLAS 主聊天、建模与分析工具、智能几何解读、工程恢复与报告。本文为设计方案，尚未实现；性能与验收数字均为拟定目标。

## 1. 建议决策

建设一个由现有 Python 后端承载的工程记忆服务，两条 LLM 链路使用同一个上下文编译入口。采用 **SQLite + 有来源的结构化记忆 + 可回放事件 + 按任务检索 + 版本失效**。

核心原则：**记忆负责保存设计意图、证据关联和任务连续性；工程模型、几何内核与求解器负责当前事实。** LLM 可以提出记忆，不能把推测自行升级为工程事实，也不能通过记忆改变执行权限。

首版无需引入独立向量数据库、图数据库或新的 agent 框架。关系和依赖先用 SQLite 表表达；语义检索与经验归纳在实际评测表明有收益后增加。现有 DeepSeek 调用可继续使用，记忆服务不绑定供应商。

评审时建议优先确定三件事：记忆与工程版本的绑定方式、意图与实测的分离规则、两条链路统一上下文的边界。它们比选择 embedding 模型更影响工程正确性。

## 2. 当前系统的缺口

| 当前实现 | 对使用的影响 | 新方案 |
| --- | --- | --- |
| 主聊天在模块变量中保存 API 历史 | 刷新后丢失连续性，不能恢复完整工具协议 | 持久化会话事件与完成检查点 |
| 超过 30 条消息后截取末尾约 28 条 | 早期要求可能丢失；消息少但脚本大时仍可能超预算 | 按 token 编译，保留必要事实与完整工具交互组 |
| 工程快照放入每轮 system prompt，包含完整脚本 | 大量重复输入，缓存和上下文利用不稳定 | 稳定规则、版本化快照、按需代码分别装配 |
| 几何解读独立请求，不读主聊天 | 对话中说明的用途不能自然影响标注 | 同源工程记忆，按所选对象检索 |
| 类型、名称、数值的证据等级不同 | “六角头”“17 A/F”等推断容易被当作事实 | 原生类型、功能推断、要求、实测分栏记录 |
| `artifactId` 和输入指纹已有失效保护 | 已具备基础，但不覆盖跨会话的需求和决策 | 复用并扩展为记忆依赖校验 |

工程库目前保存在浏览器 localStorage，后端保存原生制品。新设计必须明确迁移后的版本权威，不能另造一份会与前端悄悄分叉的“当前工程”。

代码依据：[主聊天](../src/services/deepseekAgent.ts)、[工程上下文](../src/core/llm/tools.ts)、[几何解读](../src/services/selectionAnalysis.ts)、[工程持久化](../src/core/projects.ts)、[测量状态](../src/state/inspectionStore.ts)。

## 4. 六类记忆，各自解决不同问题

| 类型 | 保存什么 | 写入与有效期 |
| --- | --- | --- |
| 当前任务状态 | 目标、正在做什么、已完成步骤、未决问题、停止点 | 按任务保存；完成后转历史，不永远常驻 |
| 设计语义 | 用户要求、接口用途、对象角色、已作决定、理由及假设 | 明确作用域；变更时保留旧版本和替代关系 |
| 工程证据索引 | 测量、分析、校验、脚本与原生制品的引用 | 工具成功写入；依赖版本相符才可作为当前证据 |
| 交互与执行经历 | 用户发言、工具参数与结果、失败及修复过程 | 追加事件；用于恢复和解释，不整段常驻上下文 |
| 可复用操作经验 | 已验证的 API 用法、特定失败的解决条件 | 带内核/API 版本与验证记录；不自动改系统规则 |
| 用户偏好 | 语言、单位展示、标注风格、信息密度 | 明确记住或在偏好设置中编辑；默认不跨工程传播设计约束 |

“最新模型的体积”不是依赖 LLM 记住的一句话，而是可以由当前 `artifactId` 找到和验证的证据。类似地，要求的孔径与测得的孔径要分别建记录。

固定系统规则、权限与工具 schema 属于程序配置，不能由经验或记忆覆盖。模型的隐藏推理文本不作为长期知识提取来源。

## 5. 总体组织

```text
ATLAS 主聊天 / 智能几何解读 / 报告与分析入口
                    │
             ContextService
       ┌────────────┼────────────┐
    当前工程快照   记忆检索与校验   会话与任务检查点
       └────────────┼────────────┘
              ContextEnvelope
                    │
                LLM 调用
                    │
            输出校验 / 工具执行
                    │
       成功证据、用户声明、任务事件
                    │
          MemoryWriter / 候选整合队列
                    │
       SQLite + 现有 CAD/FEA 制品存储
```

这是逻辑模块划分，不要求增加多个常驻服务或多个 agent。先在现有 Python 服务内实现，保持 CAD/FEA 子进程职责不变；LLM 调用复用现有代理，避免复制鉴权逻辑。

前端两个入口不再各自手工拼装工程记忆。它们提交任务类型、当前问题、关注点、选择和版本；ContextService 返回各自允许的上下文。

## 6. 数据契约：每条记忆都能回答“从哪里来、还适用吗”

建议的最小字段如下，实际实现使用严格 JSON Schema：

| 字段组 | 字段及含义 |
| --- | --- |
| 身份与隔离 | `id, schemaVersion, projectId, sessionId, taskId, branchId`；用户偏好另有 `userId` 作用域 |
| 内容类别 | `kind`：requirement、decision、assumption、observation、hypothesis、experience、preference、task |
| 命题 | `subjectId, predicate, value, unit, qualifiers`；保留原文、规范化单位及公差条件 |
| 适用对象 | 工程 / 部件 / 语义特征 / 原生对象；原生引用必须含 `artifactId + topologyId` |
| 证据 | `sourceType, sourceEventIds, evidenceRefs, method, tolerance`；来源可为用户、内核、求解器、导入文档、LLM |
| 认识状态 | declared、verified、inferred、unknown；不使用 LLM 自报百分比来授权写入 |
| 生命周期 | `status`：candidate、active、conflicted、stale、superseded、retracted、deleted |
| 时间与版本 | `recordedAt, validFrom, validTo, projectRevision, dependencies, supersedesId, revision` |
| 外发与隐私 | `visibility, allowedPurposes, exportPolicy`；独立于召回相关性判断 |

数值命题必须带量纲，数值与单位分开保存。来源文档明确给定公差时保留原文、标准版本和适用条件；只说“精密配合”不能自动补成某个公差等级。用户说“孔径 10”而当前单位明确为 mm，可以规范化为 10 mm，并记录单位来自工程约定。

同一事实的内容修订采用新修订记录，旧版本保留；状态变化写入审计事件。`recordedAt` 表示系统何时知道，`validFrom/validTo` 表示何时适用，避免“今天录入的旧报告”覆盖今天的模型。

示例：

| 记录 | 类别 / 状态 | 来源 / 依赖 |
| --- | --- | --- |
| 接口孔要求直径 10 mm | requirement / active / declared | 用户消息 E101；语义特征 F12；适用于当前设计分支 |
| F12 关联面测得直径 9.8 mm | observation / active / verified | 内核测量 E108；artifact A；测量方法与容差 |
| 该孔可能用于轴承定位 | hypothesis / active / inferred | LLM 解读 E109；证据对象列表 |

前两条形成“要求与实测偏差”，不是记忆冲突；第三条不进入“已确认用途”。是否满足要求还取决于用户是否定义了公差，不能自行判定合格。

## 7. 写入流程：先记录事件，再形成有条件的记忆

1. 用户消息和工具结果先以事件形式落盘，分配唯一 `eventId`。
2. 工具成功结果由确定性代码生成证据索引；失败和未完成结果只生成经历，不生成成功事实。
3. 自然语言提取器只输出候选记忆，必须引用原始消息片段或工具结果字段。
4. 校验作用域、对象引用、单位、来源、重复命题、冲突及依赖。
5. 明确且无歧义的用户声明可自动记为 declared；内核/求解器结果通过校验后记为 verified。模糊对象指代、推测用途和自动归纳保持 candidate 或 inferred。
6. 同事务提交记忆修订、依赖和审计记录。异步提取采用 outbox、唯一任务键和重试，崩溃后可接续。

紧要路径与后台路径分开：当前用户请求、明确设置和工具成功事实立即可用；长历史归纳和经验整理在后台按新增事件范围增量处理。首版可在当前回答完成后处理，不启动“反思 agent 群”。

用户明确说“改成 12 mm”时，记录“目标改为 12 mm”，但必须等工具成功后才记录“模型已改为 12 mm”。失败时两者不能混为一谈。

只在不能可靠解析且会改变下一步动作时询问，例如同一工程有两个孔而用户只说“把那个孔改小”。其他情况直接展示可撤销的记忆结果，不增加逐条确认流程。

## 8. 冲突、更新与失效

### 8.1 冲突不是简单的“最近一句话优先”

只有同作用域、同对象、同语义、相交有效区间的互斥命题才进入冲突判定。要求、观测、假设分别比较；单位先规范化。

- 用户明确修正自己的要求：旧要求 superseded，新要求 active，记录修正来源。
- 工程实测值只能来自有效的内核、求解器或确定性计算工具结果。LLM 负责选择测量、调用工具和解释证据，其自行生成的数字不得写入实测记录；用户要求、设计假设和实测分别保存。
- 工具结果来自不同 artifact：分别保留，不作为同版本冲突。
- 两份规范对同一接口要求不一致：conflicted，并把来源、差异带给用户；不让相似度或时间戳决定采用哪份。
- 用户的最新发言可以改变需求，不能改变已经发生的测量记录；实现会产生新的测量。

### 8.2 依赖决定失效粒度

| 发生变化 | 保留 | 需要失效或重算 |
| --- | --- | --- |
| 几何 artifact 变化 | 工程用途、设计目标、历史决策 | 旧拓扑绑定、局部测量、网格和依赖几何的分析 |
| 材料密度变化 | 几何尺寸、面积、体积 | 质量、质量惯性及受相关材料属性影响的结论 |
| 弹性参数或屈服强度变化 | 原生几何测量 | 相应分析结果或安全系数；首版可按完整材料指纹保守失效 |
| 载荷、约束、分析体或网格变化 | 与之无关的设计要求、几何证据 | 对应 study 指纹下的 FEA 证据 |
| 用户修订用途或关注点 | 原始测量 | 参数推荐、功能解释与其派生摘要 |
| 撤回或删除某条来源 | 无关事件和事实 | 来源派生记忆、摘要、缓存及检索索引 |

依赖包含几何、材料、工况、设计语义、内核版本及测量算法版本；不能只用材料名称或界面模型名称当缓存键。每次检索和执行均重新检查依赖，后台失效更新只是加速措施。

### 8.3 跨版本的面绑定

`body-0/face-3` 只能在所属 artifact 内解释。重新建模后，即使编号相同也不能自动复用。

为有用途的对象增加稳定的 `semanticFeatureId`，如“轴承配合孔”。它与原生面的绑定独立存储。首选建模过程的特征谱系或明确命名；几何签名与邻接匹配只生成重绑定候选。匹配歧义时进入 needs_rebind，不向原生工具提交猜测的面 ID。首版不承诺自动解决 CAD 拓扑命名问题，允许用户重新选面完成绑定。

## 9. 读取流程：共同记忆，各取所需

检索顺序必须是：

1. 固定 `projectId + branchId + projectRevision + artifactId` 读取快照，确认当前任务和访问边界。
2. 精确取当前要求、适用决策、未决冲突、当前任务以及所选对象的绑定。
3. 检查来源和依赖；不把 stale、retracted 或其他工程数据放进当前事实区。
4. 按问题与对象补充历史经历和经验。首版为结构化过滤、关键词和全文检索；中文术语用受控分词/词典，不能假设默认英文分词能可靠检索中文。
5. 后续可加本地语义向量并与全文结果合并；先过滤权限和版本，再按相关性、来源等级、依赖距离和时效排序。
6. 去重、带入必要的反例或冲突，按预算编译。相关的未决冲突不能因排名靠后被静默丢弃。

对于“现在孔径多少”，必须找当前内核证据，必要时重测；对于“为什么之前改孔径”，检索历史决策；对于“继续上次任务”，恢复任务检查点。三者不能共用一个纯相似度 Top-K。

每次上下文返回 `contextId、快照版本、memoryRevision、includedIds、excludedReasons、来源引用、tokenEstimate`。LLM 输出与执行事件关联 `contextId`，以后可解释“为什么当时用了这条记忆”。

## 10. 上下文编译与预算

共同输入契约为 `ContextRequest`：任务类型、工程/分支/会话/任务 ID、预期版本、用户问题、当前选择、关注点和预算档位。输出 `ContextEnvelope`，由供应商适配器转换为 messages。

| 上下文块 | ATLAS 建模/分析 | 智能几何解读 |
| --- | --- | --- |
| 固定角色、权限、工具约束 | 必须 | 必须，且只读 |
| 当前工程摘要与版本 | 必须 | 精简版 |
| 当前任务与用户输入 | 必须 | 关注点与选中对象 |
| 已声明要求、相关决策、未决冲突 | 按任务 | 按对象及邻接关系 |
| 几何证据与可测量项 | 按任务取用 | 必须 |
| 完整脚本 | 修改几何时按需加载 | 默认不提供 |
| FEA 结果与材料详细参数 | 按任务提供，标明有效性 | 只有与当前问题相关才提供 |
| 最近消息与工具轨迹 | 保留完整交互组 | 不带完整聊天；带提炼出的适用记忆 |
| 历史经验 | 只取与当前 API/失败有关项 | 只取有验证依据的解释经验 |

建议首轮输入预算起点：主聊天 20k tokens，几何解读 8k tokens。这是待评测的产品预算，须由供应商上下文上限减去输出、工具 schema 和安全余量后约束，不是模型能力声明。

主聊天可先分配：规则/工具 4k、工程与任务 3k、适用记忆 3k、近期交互 6k、按需制品 4k；允许块间借用。完整脚本超过预算时提高经批准的任务档位或通过结构化编辑工具分段处理，不能随意截断 Python 脚本后声称可以完整修改。

压缩以“完整 user/assistant/tool 交互组”为边界，保存工具调用 ID 与配对结果。接近预算阈值时生成任务检查点，保留目标、要求、决定、未决问题、当前版本和待执行项，归档大体积原始结果并保留引用。摘要附带所依据事件区间和失效依赖；不对旧摘要无限递归总结来积累误差。

开启供应商思考模式时，当前工具交互需要的推理字段按该供应商协议保存和恢复；它们不被提取成长期知识，不进入跨链路共享记忆，也不靠裁剪破坏协议。

编译时 system/developer 区只包含程序维护的规则。召回记忆、用户文档和工程说明放在明确标识的数据区或工具结果中，附来源及状态，不把历史中的指令文本拼接成新的高优先级规则。当前请求与历史要求的冲突通过设计状态规则处理，不由 prompt 拼接顺序隐式解决。

## 11. 持久化、并发与执行恢复

SQLite 保存：projects/branches/revisions、sessions/tasks、events、memory_items/revisions、evidence_refs、bindings、dependencies、checkpoints、context_manifests、outbox、audit。大脚本、原始测量与 FEA 结果继续按内容哈希保存在文件制品中，库中保存引用与完整性校验；不把 STL、USD 或全量网格塞进记忆文本。

采用 WAL、短事务和有界写重试；`expectedRevision` 乐观并发控制，冲突返回可重读的 409。SQLite 事务保证同库内的记忆与事件一致；文件采用先写临时文件、校验、原子提交，再登记引用，启动时清理孤儿制品或重试未完成登记。备份采用 SQLite 在线备份及制品清单，不能只复制正在写入的数据库文件。

部署边界是单机本地磁盘：WAL 仍只有一个同时写者，不把数据库放到网络共享盘；如未来需要多主机协作，再迁移到服务端数据库。实现时按 [SQLite WAL 官方说明](https://sqlite.org/wal.html) 配置与验证并发、检查点和持久性，按 [在线备份接口](https://sqlite.org/backup.html) 完成恢复演练；不能将“已开启 WAL”等同于所有崩溃场景都已验证。

**目标状态：后端管理已提交工程版本，前端 Zustand/localStorage 是展示缓存。** UI 编辑和工具修改都通过同一提交边界产生修订。LLM 上下文读取一个固定修订；工具执行前比较预期修订与输入指纹。版本变化时重新读取或返回冲突，不使用已过期上下文自动提交。

迁移过渡期仍以当前前端工程为准：先在后端登记不可变快照及其规范化哈希，记忆绑定该快照；检索回来由前端再次核对哈希，并沿用现有 stale/sequence 校验。此阶段后端仅是快照与记忆服务，不作为独立的“最新工程”权威。完成统一提交入口后再切换工程版本权威，避免隐蔽双写。

工具执行必须区分 planned、started、succeeded、failed、unknown。请求使用幂等键；崩溃时已 started、未有最终结果的建模或分析任务先按任务 ID 查证，不能仅因聊天没回复就自动执行第二遍。记忆不能保证分布式 exactly-once，目标是可检测、可核对、可幂等地恢复。

切换模型仅更换供应商会话适配，不删除工程长期记忆。切工程隔离会话和召回；刷新后能恢复任务检查点。跨模型恢复时可从任务摘要重新开始，不盲目重放不兼容的推理协议。

## 12. 内部运行、自然语言纠错和外发边界

记忆系统服务于 LLM 交互与上下文编译，前端不提供记忆管理面板，也不要求用户填写、编辑或选择记忆条目。每轮自动保存用户原话、任务理解和执行来源，维护承接、修订、取消、澄清关系。原话不重写；理解属于 agent_interpretation，不冒称用户已经确认。

用户通过正常对话补充或纠正，例如“不是密封面，是安装面”“孔径改成12，其他不变”“忽略之前的重量限制”。Agent 引用该消息更新适用状态，保留原有来源与替代关系。用户明确要求忘记时，内部工具删除来源派生数据。只有无法确定重要指代或互斥要求的生效关系时，才提出简短澄清，不把维护责任交给用户。

来源清单、检索详情和修订日志仅作为内部诊断与开发者测试接口，不进入模型 HUD 或日常产品流程。

记忆默认保存在本地后端。跨工程召回只允许用户明确设置的偏好或显式共享的经验，不能以“同一个用户”为由带出其他工程的设计数据。外发另做目的白名单：几何解读只发送相关几何与语义，建模按任务发送脚本；召回到的文档文本不能改变系统规则或执行权限。导入工程包的记忆先进入隔离候选区，核验来源与制品引用后再激活。

访问主体由应用会话/后端确定，不能采信 LLM 提交的 `userId` 或 `projectId` 作为授权依据。当前单用户本地部署也要做工程归属校验；若扩展到多用户，身份与 ACL 必须在检索、直接读取、导出和写入四条路径同时生效。

“撤回”保留历史审计，“忘记”删除相应正文及派生摘要、索引和缓存；审计只留无正文的删除记录。备份按留存策略过期，并说明备份删除窗口。首版建议原始执行轨迹默认保留 30 天、设计要求和决定保留到用户删除；该天数是可配置产品策略，不是技术限制。不得存储 API 密钥到记忆中。

## 13. 与当前代码的落地接口

下列为拟新增模块/接口，不代表已经存在：

| 位置 | 职责 |
| --- | --- |
| `server/memory_store.py` | SQLite 迁移、作用域、记忆修订、事务与依赖查询 |
| `server/context_service.py` | 快照校验、检索、失效过滤、任务预算与上下文清单 |
| `server/memory_pipeline.py` | 事件提取候选、确定性验证、outbox 与归纳队列 |
| `src/services/agentContext.ts` | 两条 LLM 链路共用的 ContextRequest/Envelope 客户端 |
| `src/state/inspectionStore.ts` | 传入对象绑定与快照版本，继续拒绝过期结果 |
| `src/services/deepseekAgent.ts` | 用持久化会话/任务检查点替换模块级唯一历史；保留供应商适配 |
| `src/services/selectionAnalysis.ts` | 加载对象相关的要求/用途/冲突，继续只输出测量计划 |
| `src/core/projects.ts` 与工程包 | 导入迁移标记、稳定工程 ID、记忆及证据清单导出 |

建议接口：`POST /memory/events`（幂等追加）、`POST /memory/context`（编译上下文）、`POST /memory/candidates`（提交候选）、`PATCH /memory/items/:id`（带预期修订更新）、`POST /memory/bindings`（验证重绑定）、`GET /memory/context/:id`（查看清单）、`POST /memory/export` 与 `POST /memory/forget`。

记忆提议接口不接受客户端直接声明 `verified`；只有与后端成功工具记录相符的结果能够获得该状态。LLM 不直接写数据库或自由执行检索 SQL。

## 14. 验收方案：正确召回之外，还要防止错误执行

建立固定的 CAD/CAE 回放集，首版建议至少 60 条，包含中文表达、同名部件、多轮修订、长脚本和跨会话恢复。涉及几何数值的测试使用真实内核；LLM 提取和规划先用固定响应隔离测试，真实模型测试另记模型与 prompt 版本。

| 场景 | 必须发生的行为 |
| --- | --- |
| 聊天说“此面用于密封”，随后拾取该面 | 解读能检索到声明的用途，选择相关可测项；缺少粗糙度等依据时明确缺失 |
| 要求孔径 10 mm，测量为 9.8 mm | 两条记录并存，指出偏差与缺失公差，不覆盖任何一条 |
| 用户明确把目标改为 12 mm，建模失败 | 当前目标是 12 mm；当前实测仍是旧几何，不声称已改好 |
| A/B artifact 都有 face-3 | 不跨 artifact 套用绑定或旧测量 |
| 换材料但不改几何 | 尺寸仍可用，质量及相关分析按依赖失效 |
| 换网格或载荷 | 旧 FEA 不作为当前有效校核依据 |
| 刷新或切换模型供应商 | 工程要求和任务可恢复；工具协议兼容处理 |
| 多窗口同时改要求或工程 | 修订冲突可检测，无静默覆盖 |
| 工具成功后浏览器崩溃 | 恢复后查到成功记录，不重复执行 |
| 撤回来源或执行忘记 | 派生记忆、摘要、缓存不继续召回正文 |
| 导入文档夹带“忽略规则” | 作为文档内容，不改变 agent 权限与工具边界 |
| 问一个从未定义的公差 | 回答未定义或需要依据，不从相似零件记忆中补造 |

拟定发布门槛：固定隔离集跨工程泄漏 0 例、旧版本证据用于当前动作 0 例、未成功工具被记为成功 0 例、未知公差等被补造 0 例；核心需求召回率与冲突检出率均至少 95%。这些是有限测试集的发布门槛，不是对所有输入的零风险保证。

成本与性能单独测量：在约定开发机、单工程 1 万条记忆、无 embedding 和 LLM 的条件下，编译检索 p95 目标小于 200 ms；外部提取与生成延迟分开报告。相同任务对比当前实现、仅摘要方案和本方案，记录正确率、token、成本、端到端延迟和错误动作数；收益必须在工程回放上测得，不能照搬通用 benchmark 排名。

每次运行保留上下文清单、召回来源、失效原因、写入修订、token 估计与实际用量。没有命中也要可解释：未记住、索引未更新、对象失效、权限过滤或预算排除，应能区分。

## 15. 分阶段实施与回退

| 阶段 | 交付 | 出阶段条件 |
| --- | --- | --- |
| A：可靠存储 | 稳定工程 ID、不可变快照、事件/会话保存、记忆 schema、内部诊断与忘记接口 | 刷新可恢复；数据迁移和恢复测试通过 |
| B：两链路共用 | 确定性工程事实、设计要求候选、对象绑定、ContextService、来源与失效检查 | 密封面跨链路、材料切换、拓扑重建回放通过；旧拼接方式可一键回退 |
| C：任务与执行恢复 | token 压缩、任务检查点、幂等执行记录、后端工程版本提交边界 | 中断恢复、并发冲突、重复提交与长脚本测试通过 |
| D：有评测的增强 | 关键词/语义混合检索、增量归纳、经验复用 | 相对 B/C 在工程集上有明确收益，错误率不升高 |

首个可评审的实现建议覆盖 A+B：让两条链路共享同一工程的已声明意图，并可靠拒绝旧几何证据。C 完成后再宣称支持可靠的中断续作；D 不应成为基础正确性上线的前置条件。

实施采用功能开关和数据库 schema 版本。关闭增强检索后仍可使用原生工具与当前工程快照；记忆服务故障时明确“历史记忆暂不可用”，不伪造已恢复的历史。已有成功工具和工程版本提交不能因关闭记忆开关而回滚。可重建索引不备份为唯一依据，原始来源与记忆修订需能独立恢复。

现存项目只迁入实际保存的模型、脚本、材料和设计说明，并标注“迁移来源”；未持久化的旧聊天无法可靠补回，不从生成脚本反推用户已经确认的需求。现有工程编号可编辑且不等于稳定身份，迁移必须使用持久化 UUID。

## 16. 评审结论

推荐批准“有来源、可失效的工程语义记忆 + 统一上下文编译”这一方向，先打通主聊天与几何解读的工程意图，再增强任务续作和检索。

该方案的主要工程成本在版本与对象身份、写入真实性、删除传播和执行恢复，而不是向量召回本身。对 VISION 而言，能准确说明“这是谁提出的要求、针对哪个版本的哪个对象、现在还适用吗”，是记忆系统值得进入建模和分析链路的前提。

## 17. 首批实施状态（2026-10-20）

首批已实现内部持久化事件、不可变快照、有来源的任务理解、逐字引用用户声明的记忆工具、两链路共享上下文、自然语言修订/撤回/忘记、兼容供应商会话检查点和工具开始/完成记录。前端记忆面板已按用户要求移除。具体边界与验证见 [实施说明](agent-memory-implementation.md)。

多轮上下文由最新工程状态、当前任务理解、仍适用的要求、近期完整交互、有效工具输出、全文检索历史来源共同组织。使用 SQLite FTS5 和中文双字索引，支持读取原始事件分页；已有90轮后仍找回早期要求的回归用例。用户允许必要时部署开源向量数据库，目前尚未部署，需以跨表述召回评测决定是否增加。

结合实际代码采用过渡快照模式，前端仍是当前工程权威；没有额外维护后端“最新工程”指针。当前没有后台 LLM 归纳服务，主 agent 通过受验证的工具维护意图与重要声明；没有自动拓扑重绑定或跨工程经验传播。预算使用保守字符上限，不冒称精确 token 预算。任务检查点支持恢复上下文与识别未知执行，尚未提供原生长任务的幂等作业重放协议。
