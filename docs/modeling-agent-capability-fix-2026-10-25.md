# 螺母建模交互卡住：原因与修复

## 实际执行证据

只读检查现有工作区，未修改用户工程或重发模型请求。

- 任务 `97a5af25baba49038a6b71f07db6d4d6`，epoch 4，19次模型调用，当前 `waiting_user`。
- 14次成功接口查询、1次被拒绝接口查询、2次回执展开、1次记忆记录、1次构建失败。
- 最后错误 `preview existing geometry changes before submitting a build`；该轮没有成功预览，构建没有进入队列，界面作业计数却为1。
- 最后请求快照 `30a124bf4db0402da78d10e07f4a549c`：thinking=disabled，max_tokens=8192，消息顺序 system/user/system。准备空转后的附加指令要求构建，工具列表同时开放 preview_build 与 build_geometry，后端却要求已有模型必须先预览。
- 最后签名集保留了 create_line，丢失了此前查到的 create_line_segment。create_line 是无限直线，而 create_line_segment 可以连接顶点并构造闭合三角截面。部分查询结果被误当作完整能力边界。

这些证据确认调用配置、能力供给和执行协议存在缺陷；不能单凭此样本量化每个因素对远程模型质量的贡献。

## 已实现修复

1. 启用 thinking：文档准备低强度，有接口证据和有效建模要求后高强度。单次输出16384 token，网络总时限180秒，响应256 KiB。超时结果未知仍不自动重发。参数依据 [DeepSeek 官方文档](https://api-docs.deepseek.com/guides/thinking_mode/)。每次独立重建工程上下文，无不完整推理历史回放，不保存原始 reasoning_content。
2. 首次原生接口查询同时返回安装版本的精选能力索引和11个核心接口签名，含有限线段、多边形、螺旋线、扫掠与布尔运算。它明确不是完整白名单。索引固定保留在上下文，随运行时身份变化失效；查询回执仍受大小限制。
3. 查询进展识别跨轮已知签名，成功构建后保留已知能力集合，重复查询不再被误判为新知识。不同有效新接口仍可继续查询。
4. 当前模型没有本轮、本版本预览时，只开放 preview_build；有效预览后 build_geometry 使用空参数，执行保存的精确输入。工作流与协议纠正合入同一系统指令，恢复路径服从当前阶段。
5. 未开放工具、无效参数等确定未执行的请求反馈给模型纠正一次。已存在的 head/epoch 检查、取消隔离和非确定性故障暂停继续生效。
6. 实际取得 job_id 并进入等待作业状态才增加作业数。拒绝请求不再产生虚假作业数。不修补已有历史计数。
7. 模型设置页面同步展示思考模式，去除过时说明。
